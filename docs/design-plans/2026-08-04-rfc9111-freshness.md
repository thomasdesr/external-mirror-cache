# RFC 9111 Freshness, Charter-Scoped

## Summary

Add HTTP freshness handling so the mirror stops revalidating content that
upstreams have declared fresh. Today every cache hit performs a synchronous
upstream conditional GET before redirecting the client to S3. After this
change, a cached response that is fresh under RFC 9111 arithmetic — capped by
a single global constant — is served straight from S3 with no upstream
request. Upstream headers gain exactly one power: tuning how often we
double-check. What bodies get stored, and when, does not change; the one new
write is a metadata touch that re-anchors an entry's freshness window after
a successful revalidation — and fires only when re-anchoring would actually
make the entry fresh again.

The governing invariant, statable in one sentence: *store everything forever;
upstream headers only tune how often we revalidate, capped at N days; equal
validators never trigger a re-upload; stale is served on any upstream error.*

This document supersedes the immutable-only design of 2026-07-28. That design
rejected general `max-age` freshness "unless production data shows a
high-volume non-immutable upstream paying the round-trip tax"; the 22-host
production survey of 2026-07-31 is that data. Its mechanics — the AWS-clock
age model, fail-open posture, gate placement, and test approach — carry
forward unchanged.

## Problem

On a production deployment of this mirror, redundant revalidation
dominates upstream traffic under CI load:

- conditional GET storms consisting almost entirely of already-cached
  content
- an upstream round trip added to every served fetch
- enough sustained volume to draw HTTP 429s from PyPI's rate limiter
- files.pythonhosted.org dominates the traffic and marks everything
  `Cache-Control: max-age=365000000, immutable`; we ask anyway, on every
  request

The revalidation storm has already bitten in production: PyPI's CDN
strips conditional headers, so every revalidation returned a full 200 body,
S3 PutObject throttled under the re-upload volume, and clients got 502s. The
re-upload half of that failure was fixed by the etag-skip (#67); this design
removes the round-trips themselves.

A survey of the hosts behind the deployment's real traffic found the freshness
declarations trustworthy (zero lies) but diverse: `s-maxage`-only hosts,
`Expires`-only hosts, CDNs delivering responses already aged by hours
(`Age: 11866` observed from cdn.azul.com via Fastly), `no-cache` on one of the busiest hosts
(bcr.bazel.build), and validator-only hosts with no freshness
declaration at all.

## Charter

Operator-set precedence, highest first. Any conflict between RFC 9111 and
this list resolves in favor of the list.

1. **Availability outranks semantics.** The mirror exists to serve CI when
   upstreams are down or slow.
2. **Storage is ours, unconditional.** Every response that transits the
   mirror is stored regardless of upstream cache headers. `no-store`,
   `private`, and `Set-Cookie` do not prevent storage. (A seconds-old cached
   auth token served via stale-on-error keeps image pulls alive when
   auth.docker.io blips — do not "fix" token caching.)
3. **Freshness is theirs, capped.** Upstream headers decide only how often we
   double-check. Worst case of trusting them is bounded staleness under our
   cap; a failed revalidation falls back to stale-on-error regardless.

Deliberate RFC violations (policy, not drift):

- Ignore `no-store`, `private`, and the `Set-Cookie` storage prohibition.
- Ignore `must-revalidate`/`proxy-revalidate` prohibitions on serving stale
  during errors (RFC 9111 §5.2.2.2 says must-revalidate wins over
  stale-if-error; we invert that). pkgs.tailscale.com sends
  `must-revalidate`; strict compliance would strip stale-on-error from
  exactly the host that asked loudest. Stale-on-any-error coverage is never
  reduced, for any content class.
- Ignore client request cache directives entirely. It is our cache; the
  dominant client (Bazel's downloader) does not send them.

## Goals & Non-goals

Goals:

- With the flag on, files.pythonhosted.org revalidation volume drops by >99%
  (one conditional GET per object per cap period).
- bcr.bazel.build (`public, no-cache`) and all no-declaration hosts show zero
  behavior change.
- Variant correctness under mixed Accept headers (pypi.org/simple serves JSON
  or HTML by Accept with `max-age=600, Vary: Accept`).
- With the flag off, behavior is byte-for-byte today's.
- Log-derived decision counts account for 100% of fetch decisions
  (singleflight coalesces concurrent same-key requests into one decision,
  so decisions, not served requests, are the countable unit).
- Age-aware freshness: a response stored with `Age: 11866` has its remaining
  freshness shortened by exactly 11866 seconds (clamped at zero).
- Retroactive: the existing cached corpus becomes freshness-eligible after
  at most one successful revalidation per object — no re-downloads, no cache
  rebuild.

Non-goals and prohibitions:

- No per-host TTL or freshness configuration of any kind. The global cap is
  the only constant. Host-specific rows are folklore that drifts.
- No heuristic freshness (RFC 9111 §4.2.2 is a MAY; we decline). Validator-
  only hosts (apt.postgresql.org, get.helm.sh) and all OCI registry paths
  keep today's every-request revalidation.
- Do not change what gets stored, ever. This work changes revalidation
  frequency only. (Status-code discipline already holds: only 200s are
  stored, redirects are followed before caching so a 302 hop's body is never
  the artifact, and Range is never forwarded so no 206 ever arrives.)
- Do not weaken or condition `--stale-on-any-error`.
- Keep the etag-skip (#67). It remains load-bearing for the no-cache and
  no-declaration hosts that keep revalidating against CDNs that strip
  conditional headers.
- No widening of non-OCI cache keys for Vary in this design (see Vary guard);
  a follow-up design may add it if pypi.org/simple's `max-age=600` savings
  ever matter.
- No `docker-content-digest` upload-skip comparator in this design; it is an
  acceptable follow-up rider (header-equality only, same shape as the
  etag-skip, never body hashing) for the gcr.io/nvcr.io residual of ~9.5k
  unchanged-byte re-uploads per instance per 6h.

## Alternatives Considered

1. **Immutable-only freshness (the 2026-07-28 design).** Honor freshness only
   when the stored response carries `immutable`. Solves files.pythonhosted
   (the dominant traffic source) but nothing else the survey found: cdn.azul.com
   (`s-maxage=86400`, no immutable), snapshot.debian.org (`Expires`),
   pypi.org/simple (`max-age=600`). Its own escape clause — revisit with
   evidence of non-immutable hosts paying the tax — is now triggered.
   Superseded, not rejected: every mechanical decision it made survives here.

2. **Adopt a freshness library.** Verified against source, not just docs:
   `pquerna/cachecontrol` parses `s-maxage` correctly but its expiration math
   computes expiry from evaluation-time-plus-max-age and ignores the `Age`
   header entirely, so it structurally cannot satisfy the age-awareness goal.
   `bartventer/httpcache` implements RFC 9111 correctly including Age and
   Vary, but everything lives under `internal/` (unimportable) and it is a
   client-side RoundTripper cache — the wrong shape for a proxy that stores
   in S3 and serves by redirect. Using only pquerna's directive *parser*
   (`cacheobject.ParseResponseCacheControl`) was considered separately: the
   parser is sound, but its maintenance state is sleepy (last release
   v0.2.0 in April 2023, single maintainer, pre-1.0), and the operator
   preference is to avoid the dependency when the logic is small and
   self-encapsulated. Both libraries are Apache-2.0, so copying code into an
   internal package with attribution is legal; declined because the subset
   we need (directive-list parsing, delta-seconds, HTTP dates via the
   standard library's http.ParseTime, and four lines of age arithmetic) is
   smaller than the copied surface would be. Rejected: hand-roll as a small
   internal package, with the fixture table below as the compatibility
   evidence a library would otherwise provide.

3. **Fixed metadata-revalidation period (the Artifactory/Nexus model).**
   Artifact mirrors are the strongest prior art for this design's invariant:
   Artifactory, Nexus, apt-cacher-ng, and devpi all store artifacts forever
   and use a freshness period solely to control revalidation frequency. But
   they use *fixed configured periods* (Artifactory's retrieval-cache-period,
   Nexus's maximum-metadata-age) rather than upstream declarations. Rejected
   for this proxy: the survey found declared freshness trustworthy, and a
   declared value is strictly better information than a global guess —
   PyPI's own `max-age=0` canary URL only works if we honor headers.
   The fixed period survives here only as the *cap*.

4. **Host/path allowlist.** Rejected in the 2026-07-28 design and prohibited
   by the charter: configuration drift, doesn't scale, and strictly worse
   than header-keying (PyPI's canary URL would be served stale).

5. **Full RFC 9111 §4.2.3 age arithmetic.** Computing apparent_age requires
   trusting the upstream `Date` header against our clock and storing
   request/response times we do not store. We adopt the one component that
   involves no clock comparison — the `Age` header, a relative duration —
   and anchor residency to S3's write timestamp. The exposure from skipping
   apparent_age (an origin-direct response with an old `Date` and no `Age`
   gets its window measured from our upload time) is bounded by the cap.
   Rejected as primary; partially adopted.

## Recommended Design

### Freshness model

A cached entry is served without revalidation exactly when ALL of:

- the flag is enabled,
- `cache.Head` returned a cached entry,
- the stored headers declare an explicit freshness lifetime (see precedence
  below),
- the stored `Cache-Control` does not contain `no-cache` (RFC 9111 §5.2.2.4:
  may store, must revalidate before every reuse). The RFC gives the
  argumented form `no-cache="field-name"` weaker semantics (only the named
  fields need withholding); we deliberately treat any `no-cache`, argumented
  or bare, as disqualifying — over-conservatism that fails open to
  revalidation,
- the Vary guard passes (see below), and
- both freshness axes hold, each with strict inequality (RFC 9111 §4.2:
  equality is stale): current_age < declared_lifetime (the RFC axis,
  Age-corrected, uncapped), and resident time — now minus stored-at — is
  under the cap (the residency axis; see The cap below). The axes are
  deliberately independent: min(declared, cap) compared against
  current_age would count CDN residency reported in `Age` against our
  cap, and CDN-fronted immutable content routinely arrives already aged
  past any reasonable cap — under min() semantics exactly the host this
  feature targets could never be fresh, and the touch could never re-arm
  it.

Lifetime precedence, per RFC 9111 §5.2.2.10 and §4.2.1 for a shared cache:
`s-maxage`, else `max-age`, else `Expires` minus `Date` (when `Date` is
absent, `Expires` minus stored-at — RFC 9110 §6.6.1 lets a recipient assume
`Date` is reception time, and stored-at is our reception time). No
declaration means no fresh window — never heuristic, never infinite.
`immutable` (RFC 8246) carries no special weight; the hosts that send it also
send `max-age`, which does the work.

Directive parsing is a proper split of the comma-separated directive list
across all `Cache-Control` values, case-insensitive token match, quoted-string
aware — not a substring search. Every ambiguity fails open, and fails all
the way open: a lifetime directive that is present but duplicated,
garbage, or overflowing disqualifies the declared lifetime outright rather
than reading as absent — falling through would let ambiguity in the
strongest directive grant a window a weaker one declares (`s-maxage=0,
s-maxage=0, max-age=<big>` must revalidate, not inherit max-age's year).
An absent `Age` counts as zero; an unparseable or negative `Age`
disqualifies freshness outright — counting garbage as zero would make the
entry look younger and reward malformed input with a fresh serve. Parsed
delta-seconds are additionally bounded to half the representable duration
range so the age sum (elapsed + Age) can never overflow into a negative,
permanently-fresh reading. The feature can only remove upstream
requests that were provably unnecessary; it can never produce a new error
path.

### Age computation

current_age = (now − storedAt) + storedAge, where storedAt is the S3
object's `LastModified` (our upload time, already returned by HeadObject and
currently discarded in `s3HTTPCache.Head`) and storedAge is the stored `Age`
header's delta-seconds value, else zero. This trusts only AWS clocks plus one
upstream relative duration. It is what makes the feature retroactive: every
existing object already has `LastModified` and verbatim stored response
headers, so the corpus causing the storm becomes eligible after at most one
successful revalidation per object (see below), with no re-download.

### Advancing the window on successful revalidation

current_age grows monotonically, and neither successful-revalidation path
(304, or 200 with matching strong ETag) calls `Put`. Without a counter-
mechanism, every object would get exactly one fresh window after its last
full-body upload and then be cap-expired forever — files.pythonhosted.org's
CDN strips conditional headers and answers etag-matching 200s, so its
objects would never re-`Put` and the feature would decay to today's behavior
within one cap period. This is also the one place RFC 9111 has a MUST we
otherwise miss: §4.3.4 requires updating the stored response from a
validating 304.

So: on a successful revalidation, the cache entry may be *touched* — an S3
metadata self-copy (CopyObject onto itself with replaced metadata) that
advances `LastModified` to now and rewrites the stored headers. The body is
never rewritten, and the touch runs only when the flag is on: flag off is
byte-for-byte today's behavior, new writes included.

The copy is conditional. Singleflight serializes only within one instance,
and the fleet is several instances against one bucket, so a touch can race
a concurrent `Put` from another instance that fetched a *changed* body; an
unconditional self-copy landing after that `Put` would either roll the
body back or stamp the new body with the old validators — and mark the
result fresh for up to the cap. The copy therefore carries
`x-amz-copy-source-if-match` with the S3 object ETag the deciding `Head`
returned; a body replaced in between turns the touch into a 412
precondition failure, absorbed by the same fail-open path as any other
touch error. The copy must also re-supply the S3 system metadata that
`Put` establishes — `ContentType` at minimum — because CopyObject's
REPLACE directive resets any system field not explicitly carried; a
user-metadata-only copy would turn every touched object's Content-Type
into `binary/octet-stream`.

The new stored headers are a *merge*, per §4.3.4: fields the 304 (or
etag-matched 200) provides replace their stored counterparts; fields it
omits are retained. Replace-instead-of-merge fails quietly — a 304 that
omits `Cache-Control` would erase the freshness declaration on first
revalidation and silently demote the entry to per-request revalidation
forever. Two headers are excepted from "omitted means retained", because
they describe the response that carried them, not the content. `Age` is
taken from the validating response, else zero: a stored `Age` measures the
CDN residency of a response long gone, and inheriting it would permanently
shorten every re-armed window (cdn.azul.com's `Age: 11866` would dock 3.3
hours from every window forever). `Date` is taken from the validating
response when present, else dropped — never inherited, because
`Expires − Date` is only meaningful when both timestamps come from the
same response, and no synthesized value is needed: the lifetime rule's
`Expires` minus stored-at fallback already anchors to the touch time (RFC
9110 §6.6.1's reception-time assumption).

Two further bounds on the merge. Body-describing fields
(`Content-Length`, `Content-Encoding`, `Content-Range`, `Content-Type`)
are never updated from a validating response — a 304 carries no body for
them to describe (RFC 9111 §3.2 excludes them from stored-response
updates). And the merged set is serialized through the same metadata
allowlist as `Put`. The allowlist pass is load-bearing for the
retroactive corpus: objects stored before the allowlist carry near-2KB
full header sets (PyPI's 1155-byte CSP alone), and writing those back
plus the merged fields would exceed S3's 2KB user-metadata cap —
permanently failing the touch on exactly the objects the feature exists
for. The first touch therefore strips a pre-allowlist object's
non-allowlisted headers.

The touch fires iff the merged headers would make the entry fresh at the
instant of the touch — the gate's own decision function evaluated at
now = storedAt, where resident time is zero and current_age is whatever
`Age` the validating response carried — and
never when the validating response carries an ETag that does not
strong-match the stored one. That is §4.3.4's own MUST NOT: an IMS-only
revalidator answering 304 for changed content advertises the new ETag, and
touching would relabel the old body with it, poisoning every future
revalidation (the stale body would strong-match forever). A validating
response with no ETag is safe — the merge retains the stored validators.
Otherwise it is skipped: advancing the clock of an entry that can never
pass the gate changes no future decision, so the write buys nothing. The
skip is what bounds the cost. No-declaration entries, `no-cache` entries,
and Vary-mismatched entries revalidate on every request (bcr.bazel.build,
among the busiest hosts, is `no-cache`); an unconditional touch would have
added an S3 write per request on exactly those always-revalidating hosts.
With the skip, touches happen only when a freshness-eligible stale entry
revalidates — once per object per fresh window — so the storm that
produced hundreds of thousands of redundant conditional GETs produces at most one self-copy per distinct
object per cap period, strictly cheaper than the PutObject volume the
etag-skip already eliminated.

One cost the residency split makes real: CDN-aged large objects are
touch-eligible for the first time (under min() semantics their Age kept
the touch gate from ever passing), and CopyObject physically re-copies
the body server-side even though only metadata changes. For a multi-GB
wheel that is seconds of synchronous copy on the triggering request and
its coalesced singleflight waiters, once per object per cap window —
amortized against a cap period of zero upstream traffic for that
object. The short-cap soak (Phase 4) is where this latency gets
measured against real object sizes; an async touch was considered and
declined (it buys back once-per-window latency at the price of a
background write path), so if the soak shows the copy hurting, the
lever is a touch-size threshold, not concurrency.

Header transitions propagate in both directions. An upgrade (`no-cache`
stored, `max-age=86400` on a later 304) makes the merged entry
fresh-eligible, so the touch fires and upgrades it in place — the next
request is served fresh. A downgrade needs no write: the touch is skipped,
the entry ages past its stored lifetime, and it revalidates per-request
from then on; the stale stored declaration is harmless because the age
check fails permanently. One asymmetry, accepted: an upgrade whose 304s
omit the new headers propagates only when the body next changes (a full
re-`Put`) — bounded, and identical to today, where nothing persists 304
headers at all. The never-inherit `Date` rule makes `Expires` an absolute
deadline: an Expires-based entry re-arms only when the validating
response supplies a fresh `Expires` (or a max-age), because a retained
`Expires` minus the touch-time anchor is a lifetime already in the past —
the gate fails and the touch is skipped. An origin that declares
freshness via `Expires` but omits it from 304s therefore decays to
per-request revalidation at the original deadline: strict-RFC behavior,
today's behavior, and a host shape absent from the survey
(snapshot.debian.org, the Expires fixture, sends fresh values). (Skipping the touch for never-fresh entries knowingly
skips §4.3.4's stored-response update for them; the charter already
subordinates the RFC, and their stored headers are never consulted by the
gate.)

Failure is open: if the touch fails, the entry simply keeps revalidating —
today's behavior. One condition is skipped rather than attempted: objects
larger than CopyObject's single-part limit (5 GB) cannot be touched, and
the size is already in hand from the `Head` reply, so the touch skips
itself with a logged reason instead of issuing a failing call on every
revalidation. No multipart-copy path is built for them: no host in this
traffic serves >5 GB objects that declare freshness (the only plausible
>5 GB objects are OCI blobs, which never qualify), and an untested copy
path on the cache's one new write mechanism is worse than the degradation
it would prevent. The skip log line naming a freshness-declaring host is
the explicit trigger for a multipart-copy follow-up design — do not build
it before then. This is metadata maintenance required by the feature's own
arithmetic, not a storage-policy change: what bodies get stored, and when,
is untouched.

The freshness decision is a pure function of (stored headers, storedAt, now,
cap), living in a new internal package; only the caller in `fetchAndCache`
supplies the wall clock. The function returns the decision plus the fields
observability needs: computed age, declared lifetime, resident time,
and a reason that distinguishes "no declared lifetime", "no-cache",
"Vary mismatch", "TTL expired", and "cap expired". (No surveyed proxy —
Squid, ATS, Varnish, nginx, Cloudflare — distinguishes cap-expiry from
TTL-expiry in its logs; the distinction is cheap and the 3am operator wants
it.)

### The cap

The cap bounds resident time — now minus stored-at, the time since this
cache last stored or successfully revalidated the entry — not the
RFC current_age. It is a single global, host-agnostic duration, default
7 days, flag-configurable. Its rationale: unsurveyed hosts ride the same
catch-all client rewrite, and the cap bounds them without encoding beliefs
about any named host. The rationale is explicitly NOT "upstreams lie" —
the survey found zero freshness lies.

Bounding resident time rather than current_age is what makes the cap mean
what the charter says it means: "upstream headers only tune how often we
revalidate, capped at N days" is a bound on time between *our own*
upstream checks. A successful validation proves currency at that instant;
the cap window it re-arms should not be pre-consumed by how long some CDN
held the bytes before answering us. The standard shared-cache capping
semantic — min(declared, cap) against current_age (Varnish beresp.ttl,
ATS revalidate rules, Cloudflare edge-TTL) — breaks down here precisely
because our upstreams are themselves CDNs: hot immutable content sits
CDN-resident for weeks, so every response, first fetch and validating 304
alike, arrives with an `Age` already past any reasonable cap. Under min()
semantics those entries are cap-expired at birth, the touch's
fresh-at-the-instant gate never passes, and the flagship traffic source
is structurally excluded at any cap below the CDN's retention. The
worst-case bound on time since our own last proof of currency is
unchanged by the split — that was always the cap, and it is exactly what
the residency axis measures. What the split deliberately drops is the
incidental bound min() placed on current_age: a fresh serve's age
relative to the origin's generation time is now limited only by the
declared lifetime, CDN residency included. A 7-day cap costs files.pythonhosted.org one conditional
GET per object per week — negligible against the >99% reduction goal —
and is also what time-bounds poisoned-entry persistence (see Failure
cases).

### Vary guard

An entry is never fresh unless the request headers named by its stored
`Vary` are a subset of the headers its cache key's variant encodes. The key
today does not carry that information — `CacheKey` is URL plus an opaque
variant string — so `buildKey` additionally reports which header names the
key function folded into the variant (`Accept` for OCI paths with a
non-empty Accept; the empty set otherwise, including OCI requests that sent
no Accept). The gate compares stored `Vary` against that set: OCI
Accept-variant keys tolerate `Vary: Accept`; URL-only keys tolerate only an
absent or empty `Vary`. `Vary: *` is never fresh (RFC 9111 §4.1: never
matches). Failing the guard is not an error — the entry revalidates with
the client's own Accept forwarded, exactly today's behavior, which is what
keeps mixed-Accept clients of pypi.org/simple variant-correct today and
after this change.

One `Vary` member is exempt from the subset check: `Accept-Encoding`,
the near-universal CDN default (pypi.org's JSON endpoints send
`max-age=900, Vary: Accept-Encoding`). The guard exists to stop the gate
freezing one client population's variant as fresh for another, and that
mechanism requires the client's request headers to reach upstream — but
the mirror never forwards the client's `Accept-Encoding`; the upstream
transport sends its own uniform value and transparently decodes. The
cache therefore holds exactly one encoding variant per key, ever, and
there is no wrong variant for the exemption to serve. Without it, every
`Vary: Accept-Encoding` host is rejected on every request — a
seconds-old entry with a 900-second lifetime revalidates forever — for
an axis on which nothing varies. The exemption is terminal, not interim:
even a future per-variant keying design should not key on a header the
mirror does not forward, since that would fragment byte-identical
objects. All other `Vary` members stay strict; `Accept` in particular
guards live JSON/HTML negotiation on pypi.org/simple.

Audit of the existing variant mechanism, as the charter asks: it is an
accident with respect to Vary. It was built for OCI content negotiation,
never reads the response's `Vary`, and applies the Accept variant to every
`/v2/` path — including content-addressed `/blobs/<digest>` paths that
cannot vary by Accept, so blob entries are needlessly fragmented per client
Accept string (distinct S3 objects and singleflight groups for identical
bytes). That fragmentation is a pre-existing, non-blocking storage
inefficiency, out of scope here; the guard above is what makes the
mechanism *sufficient* for freshness correctness even though it was not
designed for Vary. The inverse gap — URL-only keys racing on
negotiating URLs outside the gate — is likewise pre-existing and
captured in docs/known-issues/2026-08-18-vary-races-on-url-only-keys.md.

Consequence accepted for v1: pypi.org/simple (`max-age=600, Vary: Accept`,
URL-only key) keeps revalidating on every request. Its 600-second windows
are not what the storm is made of; widening non-OCI keys to encode Accept
would change every existing S3 key for those paths and forfeit
retroactivity, so it is deferred to its own design if the data ever asks
for it.

### Gate placement and data flow

The gate sits in `fetchAndCache`, after the cache `Head` and before
`buildUpstreamRequest` — inside the singleflight callback, so the leader
does Head + gate + presign and all waiters share the presigned URL. The
fast-path request flow is: parse target → build key → Head → gate says
fresh → log → presign → 303. Nothing else runs:

- `FallbackPolicy` is not consulted — it decides what to do after an
  upstream attempt fails, and the fresh path never attempts upstream.
- `ociAuthTransport` only sees requests that go upstream; a fresh hit skips
  token negotiation entirely — a strict reduction in work. OCI registries in
  our traffic do not send explicit freshness, so manifests (mutable tags
  included) keep today's every-request revalidation; the Vary guard and
  per-variant keys cover the rest.
- Entries that are not fresh flow into the existing conditional fetch,
  etag-skip, and fallback machinery untouched.

### Interface change

`httpCache.Head` currently returns headers with nil-for-miss. It changes to
return a small cached-entry record (headers, stored-at time, and the S3
object ETag and size for the conditional touch and its 5 GB skip), nil for
miss, preserving the miss-contract shape. `httpCache` gains a touch operation taking the key,
the expected object ETag, and the header set to write (advance stored-at
via conditional copy, re-supplying system metadata, body untouched) for
the revalidation-advance mechanism above; the §4.3.4 merge — the Age/Date
exceptions, the body-field exclusions, and the allowlist pass — happens in
the freshness package, so the cache layer only ever stores a fully-merged
set. `buildKey` additionally
returns the variant-encoded header names for the Vary guard. Blast radius:
`s3HTTPCache` (populate stored-at from the HeadObject `LastModified`
already in hand; implement touch as a metadata self-copy), `fakeCache` in
the server tests (entry struct gains a stored-at field, stamped by Put,
advanced by touch, settable directly by tests needing aged entries), the
key funcs, and `fetchAndCache`. No changes to `Put`, `GetPresignedURL`,
`CacheKey`, or the S3 path layout.

### Observability

One new `action` value in the established structured-log vocabulary
(`cached`, `revalidated`, `refreshed`, `stale`, `error`): `fresh`, logged at
Info with the target, computed age, declared lifetime, resident time,
and `action_reason` = "within freshness lifetime". The message must not read
as an upstream response — there was none. Revalidation-path log lines gain a
freshness-reason field carrying the gate's negative reason ("TTL expired" vs
"cap expired" vs "no declared lifetime" vs "no-cache" vs "Vary mismatch"),
so every fetch decision is reconstructible from one log line and
action-counting queries quantify skipped revalidations directly.

Two honest bounds on "counts account for everything", both pre-existing:
singleflight coalesces concurrent same-key requests into one decision, so
action counts tally *decisions*, not *served requests* — under storm load
one `fresh` line can represent many coalesced 303s (per-request correlation
remains available via the reqlog request ID). And one decision path
currently logs no `action`: an upstream fetch error with no cached
fallback. The fallback-denied path already logs `action` = `error` inside
`fetchAndCache`, so the new log line goes at the no-fallback site — not
at the top-level handler, which would double-log the decisions that
already carry an action.

A masked-invalidation need (upstream sent long freshness on content that
actually changed) is by construction an upstream spec violation and surfaces
as client-side checksum failures, not anything visible to the proxy. The
operational play: age and lifetime on every `fresh` line make long-lived
entries cheap to spot; deleting the S3 object forces a re-fetch; disabling
the flag converts the question into an ordinary revalidation. No new metrics
infrastructure.

### Configuration

Two new flags, following the newer flag-with-env-fallback convention
(`--client-timeout` style), because toggling during an incident should be a
systemd-environment change, not a rebuild:

| Flag                | Env var                          | Default | Purpose                                                       |
|---------------------|----------------------------------|---------|---------------------------------------------------------------|
| `--honor-freshness` | `MIRROR_CACHE_HONOR_FRESHNESS`   | `false` | Serve fresh cache hits without revalidating.                  |
| `--freshness-cap`   | `MIRROR_CACHE_FRESHNESS_CAP`     | `168h`  | Maximum resident time before a fresh-eligible entry revalidates. |

Default OFF: one behavior change per rollout, revertible at runtime. The
flag gates both the fast path and the touch — the touch is itself a
behavior change (a new S3 write path) and must be revertible with the same
switch. The default flips to on only after validation on the dev fleet
under real storm load, as its own change.

## Failure and Abuse Cases

- **A host declares freshness on content that changes within the window.**
  We serve the stored bytes for up to min(lifetime, cap) with no upstream
  check, under a healthy upstream — new relative to today, where staleness
  only occurs under the fallback policy. The realistic regime is not the
  surveyed hosts (the survey found their declarations honest) but the
  unsurveyed long tail riding the catch-all rewrite — which is exactly what
  the cap exists to bound. Accepted per charter precedence: blast radius is
  per-object and time-bounded, and the dominant clients (pip, Bazel, uv)
  verify content hashes end-to-end, so a wrong body fails loudly
  client-side. Remedies: delete the S3 object (next request re-fetches) or
  flip the flag fleet-wide.
- **bcr.bazel.build (`public, no-cache`).** Never fresh; byte-for-byte
  today's behavior. One of the busiest hosts is deliberately untouched.
- **`max-age=0` (PyPI's canary URL).** current_age ≥ 0 is never strictly
  less than 0; always revalidates. The canary keeps doing its job.
- **`s-maxage=0` with a large `max-age`.** s-maxage wins precedence, so the
  entry always revalidates — the RFC-correct shared-cache reading, and the
  opposite of the 2026-07-28 design's documented simplification.
- **Expires without Date from a skew-broken origin.** Lifetime measured
  against stored-at; over-declaration is bounded by the cap,
  under-declaration just revalidates.
- **Aged CDN responses.** The stored `Age` shortens the declared window by
  exactly the CDN's residency; without this, Fastly-fronted hosts would get
  their windows silently extended by hours. It shortens only that axis: the
  cap measures our own resident time, so a CDN that held hot immutable
  content for weeks cannot pre-consume the revalidation window it has no
  part in.
- **Immutable response reached through a redirect from a mutable alias.**
  Redirect following is transparent and the cache key is the original URL,
  so an alias URL that redirects to a versioned artifact stores the target's
  headers under the alias's key; the fast path freezes the alias→target
  binding for up to a full fresh window (cap-bounded). Accepted, and no mechanism is
  built: no host in the surveyed traffic has this shape (the only redirect
  host, snapshot.debian.org, redirects to the artifact, not from a mutable
  alias), the exposure is per-object and cap-bounded, and the remedies are
  the same as above.
- **Cross-instance touch/Put race.** Singleflight is per-instance; two
  instances can revalidate the same stale key concurrently, one getting a
  304 while the other gets a changed 200 and `Put`s the new body. The
  conditional copy (`x-amz-copy-source-if-match` on the Head-time object
  ETag) makes the loser's touch fail with 412 instead of rolling back the
  new body or stamping it with old validators; the failure is absorbed
  fail-open. Concurrent touches of the *same* body are last-writer-wins
  on metadata, which is benign.
- **Poisoned-entry persistence.** Today a corrupted cached body heals on the
  next upstream 200; a fresh entry is not re-checked until it goes stale.
  The cap bounds this at 7 days where the 2026-07-28 design accepted
  multi-year windows — strictly better, plus the same client-side hash
  verification argument.
- **Clock skew.** Both timestamps in the age arithmetic are AWS-synced; skew
  is seconds against windows of minutes to days. Bounded and harmless at
  this policy's stakes.

## Acceptance Criteria

### rfc9111-freshness.AC1: Fresh content is served without upstream traffic
- **rfc9111-freshness.AC1.1 Success:** A cached entry with
  `max-age=365000000, immutable` stored seconds ago is served via 303 with
  zero upstream requests (flag on).
- **rfc9111-freshness.AC1.2 Success:** An entry with only `s-maxage=86400`
  is fresh within that window (cdn.azul.com's exact header set as fixture).
- **rfc9111-freshness.AC1.3 Success:** An entry with `Expires` (and `Date`)
  and no max-age is fresh within Expires−Date (snapshot.debian.org fixture);
  when both `max-age` and `Expires` are present, max-age wins.
- **rfc9111-freshness.AC1.4 Edge:** current_age exactly equal to the
  declared lifetime is stale, and resident time exactly equal to the cap
  is stale (strict inequality on both axes).
- **rfc9111-freshness.AC1.5 Edge:** remaining declared freshness — max(0,
  declared − current_age) — for a response stored with
  `Age: 11866` is exactly 11866 seconds less (clamped at zero) than for the
  same response without it; the residency axis is unaffected by `Age`.
- **rfc9111-freshness.AC1.6 Success:** after a successful revalidation (304
  or etag-matching 200) of a stale entry, the entry is fresh again without
  a body re-upload — for a full fresh window (min(declared lifetime, cap))
  when the validating response carries no `Age`, its declared axis
  shortened by exactly that `Age` otherwise.
- **rfc9111-freshness.AC1.7 Rollout:** on the dev fleet under storm load
  with the flag on, files.pythonhosted.org conditional-GET volume drops by
  >99% versus flag-off (one conditional GET per object per cap period,
  steady-state).
- **rfc9111-freshness.AC1.8 Success:** header transitions propagate both
  ways — an entry stored `no-cache` whose later 304 carries
  `max-age=86400` is touched and served fresh on the next request
  (upgrade in place); an entry whose upstream downgrades to `no-cache`
  ages out with zero cache writes and revalidates per-request thereafter.
- **rfc9111-freshness.AC1.9 Success:** an entry whose stored `Age` exceeds
  the cap (CDN-resident content) is fresh while resident time is under the
  cap and current_age under the declared lifetime, and a validating
  response carrying such an `Age` still re-arms the entry via touch.

### rfc9111-freshness.AC2: Unchanged behavior where the charter demands it
- **rfc9111-freshness.AC2.1:** `no-cache` entries (bcr.bazel.build fixture)
  revalidate on every request, flag on or off.
- **rfc9111-freshness.AC2.2:** Entries with no freshness declaration
  (validator-only fixture) revalidate on every request; no heuristic window
  is ever computed.
- **rfc9111-freshness.AC2.3:** `max-age=0` and `s-maxage=0, max-age=<big>`
  always revalidate.
- **rfc9111-freshness.AC2.4:** With the flag off, an otherwise-fresh entry
  still revalidates (exactly one upstream hit) and no touch occurs —
  flag-off is byte-for-byte today's behavior, cache writes included.
- **rfc9111-freshness.AC2.5:** OCI variant-keyed entries without freshness
  declarations behave identically to today.
- **rfc9111-freshness.AC2.6:** A successful revalidation of a never-fresh
  entry (`no-cache`, no declaration, or Vary-mismatched) performs no cache
  write: the touch is skipped whenever the merged headers would not make
  the entry fresh at the instant of the touch.

### rfc9111-freshness.AC3: Cap and Vary bounds hold
- **rfc9111-freshness.AC3.1:** An entry declaring a lifetime longer than the
  cap is stale once resident time reaches the cap, and the log reason says
  cap-expired, not TTL-expired.
- **rfc9111-freshness.AC3.2:** An entry whose stored `Vary` names a header
  not encoded in its cache-key variant is never fresh (pypi.org/simple
  fixture on a URL-only key); `Vary: *` is never fresh.
- **rfc9111-freshness.AC3.3:** An OCI variant-keyed entry with
  `Vary: Accept` can be fresh, and distinct Accept variants are evaluated
  independently.
- **rfc9111-freshness.AC3.4:** `Vary: Accept-Encoding` never blocks
  freshness — alone on a URL-only key, or alongside otherwise-satisfied
  members, case-insensitively — because the mirror holds one encoding
  variant per key by construction.

### rfc9111-freshness.AC4: Every decision is observable
- **rfc9111-freshness.AC4.1:** Every fetch decision logs exactly one action
  (`fresh`, `cached`, `revalidated`, `refreshed`, `stale`, `error`),
  including the currently action-less failed-fetch error path — no silent
  decision paths. (Singleflight coalescing means decisions, not served
  requests; the Observability section names this bound.)
- **rfc9111-freshness.AC4.2:** `fresh` lines carry age, declared lifetime,
  and resident time; revalidation lines carry the gate's negative
  reason.

### rfc9111-freshness.AC5: Fail-open totality
- **rfc9111-freshness.AC5.1:** Garbage directives, unparseable dates,
  negative or non-numeric Age, and missing stored-at all degrade to
  revalidation, never to an error response.
- **rfc9111-freshness.AC5.2:** The touch merge never destroys information
  or inherits delivery facts: a 304 omitting `Cache-Control` retains the
  stored declaration (the entry stays freshness-eligible), a 304 omitting
  `Age` re-arms a full fresh window (stored `Age` and `Date` are
  never inherited), and body-describing fields are never updated from a
  validating response.
- **rfc9111-freshness.AC5.3:** A touch whose object was replaced between
  `Head` and `CopyObject` fails its `if-match` precondition and is
  absorbed fail-open; it never overwrites the newer object.
- **rfc9111-freshness.AC5.4:** A touched entry serves the same
  Content-Type on the presigned-GET path as before the touch.
- **rfc9111-freshness.AC5.5:** A successful revalidation of an entry
  larger than 5 GB issues no copy attempt — the touch is skipped with a
  logged reason, and repeated requests generate zero copy calls.

**Goal:** `Head` exposes when the object was stored.

## Test Plan

The gate being a pure function of (stored headers, storedAt, now, cap) makes
it testable without clock injection — tests pass explicit times; only
`fetchAndCache` touches the wall clock, mirroring how the OCI token TTL
logic keeps time at its edges.

- **Fixture table (unit):** the surveyed hosts' exact header sets, verified
  against production capture: files.pythonhosted.org
  (`max-age=365000000, immutable, public`), cdn.azul.com (`s-maxage=86400`
  with `Age: 11866`), snapshot.debian.org (`Expires` and `max-age` both),
  bcr.bazel.build (`public, no-cache`), pypi.org/simple
  (`max-age=600, Vary: Accept`), a validators-only fixture
  (apt.postgresql.org shape), and PyPI's `max-age=0` canary.
- **Property tests (rapid, per house preference):** fresh ⇔ (explicit
  lifetime present ∧ no-cache absent ∧ Vary minus Accept-Encoding ⊆
  variant-encoded headers ∧ current_age < lifetime ∧ resident < cap); monotonicity (fresh at t
  implies fresh at any earlier time since storedAt); cap dominance (never
  fresh once resident time passes the cap, regardless of declared lifetime
  or stored Age); Age shift (adding Age: k reduces remaining declared
  freshness by exactly k, clamped at zero, and never trips the cap while
  resident time is under it); round-trip through the
  s3_metadata encoding yields the same decision; merge totality (for any
  stored/304 header pair: content fields come from the 304 when present
  else the stored entry, body-describing fields always come from the
  stored entry, `Age` and `Date` never do, and a 304 omitting `Age`
  re-arms exactly the full fresh window); touch-iff-fresh (the
  touch decision equals the gate's decision on the merged headers at the
  touch instant).
- **Integration (`server_test.go` patterns, upstream-hit counters):** fresh
  entry → 303, zero upstream hits; aged-past-lifetime entry → exactly one
  hit; aged-past-cap entry with huge declared lifetime → one hit; revalidated
  entry → fresh again with no further hits and no body re-upload (the touch);
  flag off → one hit; no-cache entry (bare and argumented forms) → one hit
  per request; OCI variant fixtures.
- **Mutation checks:** strict-to-non-strict inequality (both axes), cap
  removal, comparing the cap against current_age instead of resident time
  (must break the CDN-Age fixture), exempting every Vary member instead
  of only Accept-Encoding (must break the strict Vary fixtures),
  no-cache-check removal, making the touch unconditional (must break
  AC2.6's no-write-on-never-fresh test), and inheriting stored `Age`
  through the merge (must break AC5.2's full-window test) must each break
  a named test.

## Migration & Compatibility

Deploying is behavior-neutral: the flag defaults off and the `httpCache`
interface change is internal (one production implementation, one test fake).
No S3 path changes. One metadata format change, flag-on only: the first
touch of a pre-allowlist object rewrites its stored headers through the
allowlist, stripping non-allowlisted fields — reads stay permissive, so
both formats coexist indefinitely. Turning the flag on applies
immediately to the existing corpus — stored headers plus S3 `LastModified`
are already sufficient — which is a design goal, not an accident: the
existing corpus is exactly the content causing the storm.

Relationship to the etag-skip (#67) and 304-distrust (#69), both already on
main: the gate runs before the upstream request; those run after a response
arrives. Fresh entries never reach them; everything else still benefits.
All three draw `action`/`action_reason` values from one vocabulary so
production queries stay uniform.

## Decisions

- **General RFC 9111 freshness with a global cap**, superseding
  immutable-only. The survey is the evidence the earlier design asked for;
  the cap is what makes trusting the long tail safe without per-host
  folklore.
- **Hand-rolled internal package, no dependency.** Verified: pquerna's
  expiration math ignores Age (fails the age-awareness goal);
  bartventer's correct implementation is `internal/` and client-shaped.
  Copying Apache-2.0 code is permitted with attribution but the needed
  subset is smaller than the copied surface.
- **AWS-clock age model.** storedAt from S3 LastModified plus the stored
  `Age` header; upstream `Date` is used only in the Expires lifetime
  subtraction, never in age arithmetic. Documented divergence from full
  §4.2.3; exposure bounded by the cap.
- **Touch on successful revalidation, only when it would re-arm a
  window.** Without the touch the cap is a one-shot window and the feature
  decays to today's behavior within one cap period; it is also the RFC
  9111 §4.3.4 stored-response update. Gated on the flag and on the merged
  headers making the entry fresh at the touch instant — never-fresh entries
  (`no-cache`, no declaration, Vary-mismatched) are never touched, which
  is what keeps the write volume at once per object per fresh window
  instead of once per request on the always-revalidating hosts.
  Conditional metadata self-copy only (`if-match` on the Head-time object
  ETag, system metadata re-supplied), fail-open, bodies never rewritten.
- **304 header update is a merge, with delivery facts excepted and body
  facts frozen.** Fields the validating response provides win; fields it
  omits are retained — except `Age` (from the validating response, else
  zero) and `Date` (from the validating response, else dropped, the
  stored-at fallback anchoring the `Expires` subtraction), which describe
  the response that carried them rather than the content, and
  body-describing fields, which a bodiless 304 cannot describe. The
  merged set is written through the same metadata allowlist as `Put`.
  Consequence, accepted: `Expires` is an absolute deadline — an
  Expires-based entry re-arms only when its 304s carry a fresh `Expires`
  or a max-age; an origin omitting both decays to per-request
  revalidation at the original deadline, which is strict-RFC behavior,
  today's behavior, and a host shape absent from the survey.
- **Cap default 7 days.** Low end of the charter's 7–14 range: cheapest to
  relax later, tightest bound on the unsurveyed tail during initial rollout.
- **The cap bounds resident time, not current_age.** Two independent
  freshness axes instead of min(declared, cap) against current_age: the
  standard min() semantic counts CDN residency reported in `Age` against
  our cap, and CDN-fronted immutable content arrives already aged past any
  reasonable cap — cap-expired at birth, untouchable, the flagship traffic
  source structurally excluded. The worst-case staleness bound (cap since
  our last proof of currency) is identical either way; see The cap.
- **Flag default off**, flipped only after dev-fleet validation. One
  behavior change per rollout.
- **Vary handled by a conservative guard, not key widening.** Correctness
  first; the 600-second revalidation savings on pypi.org/simple do not
  justify forfeiting corpus retroactivity in this design.
- **`Accept-Encoding` exempt from the Vary guard.** The guard defends
  against freezing one client's variant for another, which requires the
  client's header to reach upstream; the mirror never forwards
  `Accept-Encoding`, so one encoding variant exists per key and the axis
  cannot select a wrong one. Strictness there rejects every CDN-default
  `Vary: Accept-Encoding` host on every request for no protection in
  return.
- **Fail open to revalidation on every ambiguity.** The feature can only
  remove provably-unnecessary upstream requests.
